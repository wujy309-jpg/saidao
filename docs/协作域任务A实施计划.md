# 任务 A：协作域实施计划

## 1. 总目标

把“组队 → 协作 → 沉淀”做成一条可信闭环：用户可以安全创建和管理团队，在明确的成员权限下使用项目空间，并通过提交历史、差异和回滚沉淀成果。

本计划按阶段推进。每个阶段都有独立的完成标准，阶段之间可以暂停，不要求一天完成全部工作。

## 2. 负责范围

### 包含

- 团队创建、招募、申请、审批、成员变更、队长转让和解散
- 团队状态机、权限和通知
- 项目空间所有者/开发者/访客权限
- 仓库、分支、文件、下载和提交接口的安全校验
- 提交快照、diff 和回滚
- 团队与项目空间前端页面
- 安全复现脚本、权限矩阵和修复报告

### 不包含

- 竞赛推荐和竞赛数据补全
- 论坛分页、搜索、内容治理
- AI、Token、计费和并发控制
- 平台级登录、用户画像和管理后台整体建设

## 3. 总体排期

建议按 **8 个工作阶段** 推进。每个阶段约 0.5～2 个工作日，实际时间以代码量和联调情况为准。

| 阶段 | 名称 | 主要结果 | 优先级 |
|---|---|---|---|
| 0 | 基线和契约冻结 | 明确接口、DTO、角色矩阵和数据边界 | P0 |
| 1 | 项目空间鉴权 | 所有仓库接口按登录用户和成员角色鉴权 | P0 |
| 2 | 项目空间安全加固 | 修复接管、自提权、branch 穿越和隐私泄露 | P0 |
| 3 | 团队正确性修复 | 修复解散、队长退出、申请状态和数据约束 | P0 |
| 4 | 团队完整生命周期 | 转让、通知、招募帖解绑和成员流程闭环 | P1 |
| 5 | 版本沉淀能力 | 快照、diff、回滚和提交边界校验 | P1 |
| 6 | 前端协作体验 | 页面操作、角色展示、错误处理和批量保存 | P1 |
| 7 | 联调和验收 | 攻击复现、权限矩阵、演示和修复报告 | P0 |

## 4. 分阶段执行计划

### 阶段 0：基线和契约冻结

**目标**：先固定边界，避免后续三人协作时反复改接口。

**工作项**

- [x] 固定 `OWNER`、`DEVELOPER`、`VISITOR` 的权限矩阵
- [x] 固定团队申请状态：`PENDING`、`APPROVED`、`REJECTED`
- [x] 固定团队通知类型和通知调用接口
- [x] 固定 `UserBrief`/公开用户 DTO，禁止 A 直接返回完整 `User`
- [x] 确认论坛帖子与团队使用 `teamId` 弱引用
- [x] 确认 A 只维护团队和仓库相关表
- [x] 记录所有跨域依赖和冻结接口

**涉及范围**

- `Team`、`TeamMember`、`TeamApplication`
- `CodeRepository`、`RepoMember`、`RepoBranch`、`RepoFile`、`RepoCommit`
- `Notification` 公共接口
- `UserBrief` 及团队/仓库响应 DTO

**完成标准**

- 能拿出一页权限矩阵
- 能说明每个接口从哪里取得当前用户 ID
- A 不需要依赖 B/C 的具体实体即可编译

---

### 阶段 1：项目空间鉴权

**目标**：先保证“谁能访问哪个项目空间”正确，再扩展功能。

**工作项**

- [x] 创建仓库时从登录态确定 owner，忽略请求体 owner
- [x] 仓库详情、成员、分支、文件、下载、提交历史增加访问校验
- [x] 写操作统一校验成员角色
- [x] 所有者允许管理成员和删除仓库
- [x] 开发者允许文件写入、提交和创建分支
- [x] 访客只允许读取允许范围内的资源
- [x] 非成员统一返回 `403`
- [x] 对管理员权限建立明确例外规则

**重点文件**

- `backend/.../controller/CodeRepoController.java`
- `backend/.../service/CodeRepoService.java`
- `backend/.../entity/RepoMember.java`
- `backend/.../repository/*Repo*Repository.java`

**完成标准**

- 同一仓库用三种角色执行同一组请求，结果符合权限矩阵
- 非成员不能读取文件、下载文件、查看提交或写入仓库
- 操作者 ID 不再从 `authorId`、`userId`、`inviterId` 等请求字段信任

---

### 阶段 2：项目空间安全加固

**目标**：关闭当前已确认的高风险攻击路径。

**工作项**

- [x] 修复请求体实体直绑导致的仓库接管
- [x] 防止普通成员把自己改成 OWNER
- [x] 分支名使用白名单和长度限制
- [x] 文件路径统一规范化并拒绝越界
- [x] 防止 branch 写入 `/app/static` 或其他非仓库存储目录
- [x] 校验 branch 属于当前仓库
- [x] 仓库、成员和文件响应改用公开 DTO，去除手机号、学号、邮箱
- [x] 增加审计日志，记录敏感权限操作

**完成标准**

- 仓库接管攻击失败
- 自我提权攻击失败
- branch 穿越攻击失败
- 敏感用户字段不出现在团队和仓库接口响应中

---

### 阶段 3：团队正确性修复

**目标**：先修复会导致数据错误或团队无法结束的基础问题。

**工作项**

- [x] 创建和更新团队时禁止客户端覆盖 leader/owner
- [x] 只有队长能编辑、审批、移除成员和解散团队
- [x] 队长不能退出，也不能被移除
- [x] 被拒申请不能再次审批通过
- [x] 同一用户不能重复申请同一团队
- [x] 同一用户不能重复成为团队成员
- [x] 检查团队人数上限和招募状态
- [x] 解除论坛招募帖对团队删除的硬外键阻塞
- [x] 团队解散时清理团队成员、申请和项目空间关联数据

**重点文件**

- `backend/.../controller/TeamController.java`
- `backend/.../service/TeamService.java`
- `backend/.../entity/Team*.java`
- `backend/.../entity/ForumPost.java`
- 团队和论坛相关 Repository

**完成标准**

- 有论坛招募帖的团队可以解散
- 队长不会被操作成无主团队
- 申请状态只能按合法方向流转
- 重复成员和重复申请被拒绝

### 阶段 4：团队完整生命周期

**目标**：把组队流程做成可连续使用的闭环。

**工作项**

- [x] 增加队长转让接口和前端入口
- [x] 转让前校验新队长是现有成员
- [x] 新旧队长收到转让通知
- [x] 新申请通知队长
- [x] 通过、拒绝、移除和解散通知相关成员
- [x] 解散后保留论坛招募帖，但解除其团队绑定
- [x] 完善团队详情中的申请、成员和招募状态展示
- [ ] 视需求增加团队公告或讨论入口

**完成标准**

- 可以完整演示：创建 → 招募帖 → 申请 → 审批 → 通知 → 转让 → 解散
- 解散后招募帖仍可查看
- 所有关键团队事件都有对应通知

## 5. 每阶段的工作方式

每个阶段按以下顺序执行：

1. 读取本阶段涉及的实体、Controller、Service、Repository 和前端调用。
2. 先写接口契约或权限规则，再改业务逻辑。
3. 完成一个小闭环后立即编译或运行针对性验证。
4. 记录实际修改文件和剩余风险。
5. 通过阶段验收后再进入下一阶段。

不要在同一阶段同时大改团队、仓库、通知和公共平台文件。跨域需求先冻结 DTO 或接口，再分别实现。

## 6. 当前建议启动顺序

第一轮先完成：

1. 阶段 0：权限矩阵和 DTO 边界
2. 阶段 1：项目空间鉴权
3. 阶段 2：项目空间安全加固

这三步完成后，项目空间的接管、越权和文件泄露风险才算关闭。随后进入团队正确性和团队生命周期，最后补 diff、回滚和前端体验。

## 7. 今日四项执行计划（2026-10-01）

今天先完成四个可独立验收的安全工作包，完成后再进入团队生命周期和版本管理，不把过大的功能阶段混在同一天内。

### 任务 1：身份参数清理

- 后端创建、上传、提交统一从 JWT 获取操作者。
- 前端删除 `ownerId`、`authorId`、`inviterId` 等操作者字段。
- 成员管理只保留被邀请人的目标 `userId`。
- 验收：篡改请求中的身份字段不会改变实际操作者。

### 任务 2：分支与文件路径隔离

- 分支名限制为安全字符和长度范围。
- 创建分支时校验基线分支属于当前仓库。
- 文件路径统一规范化，拒绝 `..`、绝对路径和空路径。
- 磁盘存储根目录固定为当前仓库和当前分支目录。
- 验收：branch 穿越和文件路径穿越请求返回 `400/403`，仓库外没有新文件。

### 任务 3：公开 DTO 隔离隐私

- 仓库、成员、分支、文件、提交使用公开响应 DTO。
- 用户响应只包含 `id/name/reputation/role`。
- 不向团队和仓库接口返回手机号、学号、邮箱、密码或关联实体全集。
- 验收：接口 JSON 中不存在 `password/phone/studentId/email` 等字段。

### 任务 4：权限矩阵验收

- 固化 OWNER、DEVELOPER、VISITOR、非成员的 200/403 矩阵。
- 为项目空间读、写、成员管理和删除接口列出请求样例。
- 完成前端构建、后端构建或记录环境限制。
- 验收：能用同一组接口对四种身份给出可复现结果，并形成文档证据。
