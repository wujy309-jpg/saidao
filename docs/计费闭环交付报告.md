# 「赛道」AI 计费闭环 · 交付报告

> 范围：计费正确性、运营闭环、成本与可观测、计费测试（A/B/C/D 四项）
> 验证方式：**实机复现**（H2 临时库 + 假 API Key 打开计费开关 + 本地假上游），不是「看代码觉得对」
> 对应验收项：C-6（后台设置真 partial update）、C-8（降级/失败自动退款、流水可查）、C-9（成本可核算）、C-10（AI 可观测）
> 未包含：在线支付（二期）、平台层其它非计费项（JWT 硬化/登录防护/Flyway/AI 并发/越权 403）、主站用户端 UI 打磨

## 一、一句话结论

计费从「**先扣后用、只在抛异常时退款**」升级为「**先预留 → 成功才结算 → 失败/降级/早退一律释放**」，
并把「用户花了多少钱」和「上游真实花了多少 token / 多少钱」第一次真正对上账：
三个正在漏钱的 P0 全部修复并实机复现，后台设置不再清空收款码，退款/导出/审计/成本面板补齐，计费测试从 0 增加到 19 个。

| | 修复前（审计报告实测） | 修复后（本次实测） |
|---|---|---|
| 新用户没填画像点「AI 推荐」 | 余额 `55 → 40`，只有 `CONSUME RECOMMEND -15`，无退款，可无限重复扣 | `HTTP 400 请先完成画像问卷`，余额 `55`，**0 条扣费流水** |
| 续写时会话不存在 | 余额 `-10`，SSE 只回 `error`，无退款 | 余额不变，`CONSUME -10` + `REFUND +10`（同一 `refId`），SSE 回 `{"charged":0,"refunded":true}` |
| 上游不可用时论坛 AI 润色 | 扣 5 Token，返回原文 | 返回原文，`CONSUME -5` + `REFUND +5`，备注「AI 降级，本次免扣」 |
| 后台只提交 `{"paymentNote":"..."}` | 收款码变 `null`、`freeQuotaEnabled: false → true` | 收款码、免费额度开关**原样保留**，只改文案 |

## 二、计费模型变更（核心设计）

### 2.1 旧模型的三处结构性漏洞

1. `TokenAspect` 只在方法**抛异常**时退款（`pjp.proceed()` 外层 `catch`），
   而 `RecommendationController` 把异常就地 catch 成 HTTP 200 → 切面永远看不到失败；
2. SSE 接口绕过 AOP 手动扣费，**早退分支直接 `return`**（不是异常）→ 不退款；
3. 上游降级（返回 `null` 走兜底模板）在计费层**不可见** → 按全价收费。

三者的共同根因：**「该不该收钱」这件事没有唯一的判断出口**，散落在每个 controller 的 try/catch 里。

### 2.2 新模型

```
charge(userId, scene)      预留：锁账户扣余额 + 写 CONSUME 流水 + 写 token_charge(ref_id 唯一)
      │
      ├─ 产出有效 → settle()   结算：计入 totalConsumed（只此一次，累计消耗不会漂移）
      ├─ 降级/早退 → release() 释放：原路退回 + 写 REFUND 流水（状态机保证幂等）
      └─ 抛异常   → release()  同上
                     │
                     └─ 进程被杀 → 定时补偿任务把超时未终结的预留自动退回
```

关键点：

- **幂等**：`token_charge.ref_id` 唯一 + 状态机（`CHARGED → SETTLED | RELEASED`），重复释放不会重复退款；
- **不漂移**：`totalConsumed` 只在 `settle` 时增加，退款不需要「减回去」，因此不存在 `Math.max(0, …)` 掩盖的累计误差；
- **可对账**：长时间停在 `CHARGED` 的记录就是「扣了没退」，由 `BillingMaintenanceService` 每 10 分钟兜底释放；
- **降级可见**：`DeepSeekService` 返回结构化的 `LlmResult`（内容 + 是否降级 + usage + 耗时），
  每完成一次上游调用就回填 `BillingContext`；切面据此决定结算还是免扣；
  各业务服务的兜底分支（模板计划、规则推荐、原样返回、换任务没换掉）也会显式 `markDegraded`。

### 2.3 前置校验前移

确定性、零成本的前置校验（画像是否完整、竞赛库是否为空、会话/断点是否存在、输入是否为空）
**一律放在扣费之前**：这类请求不再产生任何计费记录，连「扣费→退款」的噪音流水都不会有。

## 五、数据库与接口变更

### 5.1 新增 / 变更的表（JPA `ddl-auto=update` 自动建表，MySQL/H2 通用）

| 表 | 说明 |
|---|---|
| `token_charge`（新） | 计费预留单：`ref_id` 唯一、`user_id`、`scene`、`amount`、`status(CHARGED/SETTLED/RELEASED)`、`finished_at`、`remark` |
| `ai_call_log`（新） | AI 调用日志：`ref_id` 唯一、`status(SUCCESS/DEGRADED/FAILED)`、`llm_calls`、`prompt/completion/total_tokens`、`latency_ms`、`estimated_cost_yuan`、`charged_tokens`、`model`、`error_type` |
| `recharge_order`（+） | `refunded_at`、`refunded_by`、`refund_reason`；`status` 增加 `REFUNDED` |
| `billing_setting`（+） | `llm_input_price_per_mtok`(默认 2)、`llm_output_price_per_mtok`(默认 8)、`pending_order_alert_hours`(默认 24) |
| `token_transaction`（+） | `TxType` 增加 `ORDER_REFUND`（订单退款冲正，金额为负） |

> ⚠️ 仍未引入 Flyway（属平台层其它项）。本次全部是**增量**变更（新表 + 新列 + 新枚举值），
> `ddl-auto=update` 可以平滑升级；但旧数据里 `total_consumed` 与新的「已结算预留」口径
> 在首次升级后会有一次对不齐（历史 `CONSUME` 里含未退款的部分），后台总览已改用新口径，
> 老流水仍可在「Token 流水」页按原样查看。

### 5.3 行为变更（需要前端/调用方知道）

- `PUT /admin-api/billing/settings` 现在是**真·部分更新**：字段缺省 = 不改。全量提交仍然工作。
- 计费接口在降级时会返回/推送 `degraded` 与 `charged` 字段：
  - 推荐：响应体 `degraded` / `chargedTokens` / `degradedReason`；
  - 助手与计划 SSE：新增 `event: degraded`，`done`/`error` 事件带 `charged`。
- `TokenTransaction.refId` 不再为 `null`（格式 `SCENE-<24位随机>`），可用于对账与排障。

## 八、上线注意

1. **先备份**：新增两张表 + 三列，`ddl-auto=update` 会在启动时自动加；H2 文件库与 MySQL 都适用。
2. **口径切换**：后台「累计净消耗」改为「已结算预留合计」，与旧流水页的 `CONSUME` 合计会不一致（旧口径含未退款部分）。这是有意的修正。
3. **补偿任务**：`saidao.billing.stale-charge-minutes` 默认 30 分钟（大于 SSE 最长 5 分钟），单批上限 `saidao.billing.stale-charge-batch=200`。上线后第一次跑会退回历史遗留的「扣了没退」记录。
4. **成本单价**：默认按 deepseek-chat 的输入 ¥2 / 输出 ¥8 每百万 token 估算，请按真实账单在「平台设置」里校准，否则毛利率是错的。
5. **降级率监控**：降级即免扣，所以降级率直接等于「免费送出去的比例」；建议把面板上的降级率 > 5% 当作告警线。
