# 「赛道」商业化与 Token 收费方案

> 版本 v1.0 · 2026-09 · 目标：把 AI 能力（全部依托 DeepSeek API）包装成可收费的 Token 体系，实现可持续盈利，并交付同域名下的独立后台管理平台。

---

## 1. 一句话商业模式

**免费额度获客 → 按量 Token 付费增值 → 卡密/人工收款变现 → 后台平台精细运营。**

平台所有 AI 能力（AI 助手、备赛计划、竞赛推荐、论坛 AI 润色/建议）统一接入一套 **Token 计量计费系统**：新用户注册送体验额度、每天送免费额度（拉新+留存），免费额度用完后按次扣 Token，用户通过 **购买套餐（卡密兑换 / 转账人工确认）** 充值。全部价格、额度、套餐由运营后台实时调整，无需改代码。

---

## 2. 为什么选「免费额度 + 按量 Token」（而非订阅制）

| 维度 | 按量 Token（选定） | 订阅制 |
|------|------|------|
| 目标用户 | 大学生，比赛季高频、平时低频 | 同左 |
| 付费心理 | 「只为我用的 AI 付钱」，几块钱即可入场 | 月付心理门槛高，学生抵触 |
| 收入波动 | 比赛季自然爆发（9-11 月、3-5 月） | 平滑但总额受转化率压制 |
| 获客 | 免费额度让用户先体验全部 AI 能力 | 试用期结束即流失 |
| 运营复杂度 | 低（套餐+卡密即可） | 高（周期、续费、自动扣款） |

后续用户量起来后，可在不改动计费核心的前提下叠加「订阅卡」（周/月/季）——本方案的订单模型已预留 `channel` 扩展位。

## 3. Token 经济模型

### 3.1 定价锚点：1 Token = ¥0.01（面值）

充值套餐按面值定价、赠送加成做梯度折扣；AI 能力按**固定 Token 单价/次**收费（用户可预期，比按字符数计费更友好），场景单价在后台可调。

### 3.2 场景定价表（默认值，后台可改）

| 场景 | Token/次 | 折合 | 说明 |
|------|------|------|------|
| AI 助手对话（含竞赛上下文） | 20 | ¥0.20 | 上下文注入竞赛规则/作品/资料，最贵场景 |
| AI 助手断点续写 | 10 | ¥0.10 | 中断后继续生成 |
| 备赛计划生成 | 30 | ¥0.30 | 流式生成完整倒排计划 |
| 备赛计划调整（一句话重排） | 10 | ¥0.10 | |
| 计划任务换一个 | 5 | ¥0.05 | |
| 竞赛智能推荐（大模型精排） | 15 | ¥0.15 | 含 Top6-8 匹配度+理由 |
| 论坛 AI 润色 | 5 | ¥0.05 | |
| 论坛 AI 智能建议 | 5 | ¥0.05 | |

### 3.3 免费额度（获客引擎，后台可调）

| 项 | 默认值 | 目的 |
|------|------|------|
| 注册赠送 | 50 Token | 新用户可免费体验 2-3 次完整 AI 能力 |
| 每日赠送 | 5 Token | 每天至少 1 次 AI 动作免费，维持日活 |
| 开关 | 总开关可一键关闭 | 成本失控时止损 |

> 成本测算：按 1000 活跃用户/天、每人领满 5 Token（约 1 次论坛润色）计，每日免费成本 ≈ 1000 次 × ¥0.01 ≈ **¥10**，换取的是充值转化机会，完全可接受。

### 3.4 充值套餐（默认值，后台可增删改/上下架）

| 套餐 | 价格 | Token | 赠送 | 折合单价 |
|------|------|-------|------|---------|
| 新手包 | ¥6 | 600 | 0 | ¥0.010 |
| 体验包 | ¥12 | 1300 | +100 | ¥0.0092 |
| 进阶包 | ¥30 | 3500 | +500 | ¥0.0086 |
| 备赛包 | ¥68 | 8500 | +1700 | ¥0.0080 |
| 冲刺包 | ¥128 | 18000 | +5200 | ¥0.0071 |

梯度折扣刺激大额充值；「备赛包/冲刺包」命名贴合比赛季场景营销。

### 3.5 成本与毛利测算（关键！）

DeepSeek 成本按保守口径（deepseek-chat：输入 ¥2/百万 token、输出 ¥8/百万 token；官方近期多次降价，实际只会更低）：

| 平台场景 | 平均单次调用 token | 单次成本估算 | 售价 | 毛利 |
|------|------|------|------|------|
| AI 助手对话（8k 上下文+2k 输出） | ≈10,000 | ≈¥0.032 | ¥0.20 | **84%** |
| 助手最坏情况（8k 上下文+8k 输出） | ≈16,000 | ≈¥0.080 | ¥0.20 | 60% |
| 备赛计划生成 | ≈6,000 | ≈¥0.024 | ¥0.30 | **92%** |
| 竞赛推荐 | ≈4,000 | ≈¥0.016 | ¥0.15 | **89%** |
| 论坛润色/建议 | ≈1,500 | ≈¥0.006 | ¥0.05 | 88% |

**结论：即使按最保守成本口径，综合毛利 ≥ 75%。** 单次调用成本波动大（上下文注入长度、输出长度），因此：
1. 所有场景单价集中在后台「场景定价」页，随时根据真实账单校准；
2. 后台「总览」页展示按场景的调用次数 → 可换算真实 API 成本，运营可视化。

## 4. 系统架构

### 4.1 总体架构（同域名部署）

```
浏览器
 ├─ /api/            → 主站 SPA（React，context-path=/api，保持不变）
 ├─ /api/admin/      → 后台管理平台 SPA（独立构建，新增）
 └─ /api/...         → 后端 REST/SSE（Spring Boot 8080，保持不变）
         │
         ├─ /token/**           用户端：余额/流水/套餐/下单/卡密兑换
         ├─ /admin-api/billing/**  后台端：总览/用户/流水/套餐/卡密/订单/场景/设置
         └─ AI 接口             @CostTokens AOP 统一扣费（助手/推荐/计划/论坛AI）
```

- 主站与后台同域名、同后端：`http://<域名>/api/` 与 `http://<域名>/api/admin/`；
- 后台平台独立 SPA：独立构建、独立登录（复用 JWT + ADMIN 角色校验），不干扰主站路由；
- 主站内旧 `/admin` 页（竞赛/用户管理）**迁入**新后台平台，主站不再保留。

### 4.2 后端新增模块（Spring Boot）

```
entity/    TokenAccount、TokenTransaction、TokenPackage、RechargeOrder、
           CardKey、TokenSceneConfig、BillingSetting
repository/ 上述各实体的 Repository（含分页/聚合统计查询）
service/   TokenService（账户/扣费/退款/免费额度/卡密/订单入账，余额悲观锁保原子）
           CardKeyService（批量生成/导出/核销）
           BillingAdminService（后台统计/查询）
annotation/ CostTokens（场景枚举标注）
aspect/    TokenAspect（AOP：扣费 → 执行 → 失败自动退款）
controller/ TokenController（用户端 /token/**）
           BillingAdminController（后台端 /admin-api/billing/**）
```

### 4.3 扣费机制（关键设计）

1. **标注即计费**：AI 接口方法上加 `@CostTokens(TokenScene.ASSISTANT_CHAT)`，AOP 切面统一处理——不改动业务代码；
2. **先扣后用，失败自动退**：进入方法前校验并扣减（悲观锁 `SELECT ... FOR UPDATE` 保证并发下余额不为负）；方法抛异常自动原路退回（记 REFUND 流水）；SSE 流式接口在控制器内显式扣费/失败退款（异步任务异常不经过 AOP）。注：LLM 返回空而走**降级模板**（非异常）时按次正常计费，如用户投诉可在后台手动调整补偿；
3. **扣费前置校验免费**：`DEEPSEEK_API_KEY` 未配置（开发/降级环境）时自动免扣，保证开发体验与「降级兜底」不被收费；
4. **余额不足**：返回 HTTP 402 + `Token 余额不足，请前往充值中心充值`，前端引导充值；
5. **流水留痕**：每笔扣费/退款/充值/赠送/调整都写 `TokenTransaction`（含场景、金额、余额快照、关联 ID），可对账。

### 4.4 数据库表（JPA ddl-auto=update 自动建表，MySQL/H2 均可用）

| 表 | 关键字段 | 说明 |
|------|------|------|
| token_account | user_id 唯一、balance、total_recharged、total_consumed、last_free_grant_date | 用户账户 |
| token_transaction | user_id、type(RECHARGE/CARD/CONSUME/REFUND/GRANT/ADJUST)、scene、amount(带符号)、balance_after、ref_id、remark | 全量流水 |
| token_package | name、price_yuan、tokens、bonus_tokens、enabled、sort_order | 充值套餐 |
| recharge_order | order_no 唯一、user_id、package 快照、amount、status(PENDING/PAID/CANCELLED)、channel、paid_at、paid_by | 充值订单 |
| card_key | code 唯一、batch_no、tokens、status(UNUSED/USED)、used_by、used_at | 卡密 |
| token_scene_config | scene 唯一、label、price、enabled、sort_order | 场景单价（后台可调） |
| billing_setting | 单行：daily_free_tokens、register_bonus_tokens、free_quota_enabled、payment_note、wechat_qr_url、alipay_qr_url | 全局计费设置 |

### 4.5 充值/卡密/订单流程

```
用户购买：
  套餐列表 → 下单(PENDING) → 看到收款码+转账说明 → 转账
      → 管理员在后台「订单管理」点【确认收款】→ 订单 PAID → 余额自动入账（幂等，防重复入账）

卡密（预生成批次，适合地推/私域/代理）：
  后台批量生成卡密 → 导出 TXT 发放给买家
      → 用户在充值中心输入卡密 → 立即到账（一次有效，防重放）
```

人工确认收款是 MVP 首选：无支付牌照、无手续费、当天可上线；订单模型已预留支付宝/微信官方支付回调的扩展位（二期）。

## 7. 部署方案（同域名）

- 后台 SPA 构建产物 `admin-console/dist` → 镜像内 `/app/admin-static/`，由 Spring `StaticResourceConfig` 以 `/admin/**` 提供并做 SPA 路由回退；
- 主站 SPA 维持 `/app/static/` 不动；主站 Router 移除 `/admin` 路由，避免与独立后台路径冲突；
- `prepare-stage.sh` 同时构建两个前端；Dockerfile（stage + backend 多阶段）同时 COPY 两个静态目录；
- 生产访问：主站 `http://8.133.220.133:8080/api/`，后台 `http://8.133.220.133:8080/api/admin/`（若挂域名/nginx，仅需把根路径 302 到 `/api/`，其余不变）。

## 8. 安全与防刷

- 余额扣减走数据库悲观锁 + 事务，杜绝并发下余额变负；
- 订单确认入账幂等（状态机 PENDING→PAID 一次性），重复确认不会重复入账；
- 卡密一次性核销，码格式随机（16 位，含校验段），按批次可追溯；
- 每日免费额度按 `last_free_grant_date` 判定，登录时发放，无法刷；
- 后台全部接口 `hasRole("ADMIN")`，审计流水不可删改。

## 9. 合规与风险提示

- **卡密/人工收款**：属虚拟商品零售，无需支付牌照；依法保留流水即可。注意卡密售卖有「网络实名」争议场景时要求用户登录后兑换（本方案已如此）。
- **支付二期**：接入支付宝当面付/微信 Native 需企业/个体户资质，在 RechargeOrder 上扩展 `channel` + 回调即可，本方案预留。
- **成本风险**：DeepSeek 断供/涨价 → 后台「场景定价」一键上调，或关闭免费额度。
- **羊毛党**：每日免费额度开关 + 按场景调用统计（总览页），异常用户可后台扣币/封禁。
