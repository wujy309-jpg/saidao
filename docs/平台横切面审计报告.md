## P0 — 正在损失收入 / 可被直接利用

### P0-1 【缺陷】竞赛推荐前置校验失败仍扣 15 Token，且无退款路径

- **证据**
  - `backend/src/main/java/com/saidao/backend/controller/RecommendationController.java:29-38`
    ```java
    @com.saidao.backend.annotation.CostTokens(TokenScene.RECOMMEND)
    @PostMapping("/generate")
    public ResponseEntity<...> generate() {
        try { ... } catch (IllegalStateException e) {
            return ResponseEntity.ok(ApiResponse.error(e.getMessage()));  // ← 吞掉异常 + HTTP 200
        }
    }
    ```
  - `backend/.../service/RecommendationService.java:50` `orElseThrow(() -> new IllegalStateException("请先完成画像问卷"))`；`:68` `throw new IllegalStateException("竞赛库为空，请联系管理员")`
  - 扣费发生在切面：`backend/.../aspect/TokenAspect.java:33` `tokenService.consume(...)` 在 `pjp.proceed()`（第 35 行）**之前**。异常被 controller 吞掉 → 切面第 36 行的 `catch (Throwable)` 永远不触发 → 不退款。
  - **实机复现**：新注册用户（无画像）调 `POST /api/recommendations/generate` → `HTTP 200 {"success":false,"message":"请先完成画像问卷"}`，余额 `55 → 40`，流水只有 `CONSUME RECOMMEND -15`，无 `REFUND`。可无限重复点击，每次都扣。
- **影响**：收入/用户信任/消费者权益。最容易被触发的场景恰是新用户第一次点「AI 推荐」（还没填问卷），一次点击白扣 15 Token（¥0.15），且投诉无据（无退款流水）。也直接违反《商业化与Token收费方案》第 125 行自己承诺的「失败自动退」。
- **修复**（S）：不要在 controller 里 `catch`；让 `IllegalStateException` 抛出去由切面退款。若必须返回友好文案，则在 catch 内显式 `tokenService.refund(userId, TokenScene.RECOMMEND, null, 15)`，或把前置校验（画像是否完整）提到扣费之前放在 `RecommendationService` 的 public 入口。建议再加一个「同一用户同场景 N 秒内失败不计费」的守卫。

### P0-3 【缺陷】降级 / 空回复仍按正常价计费（用户花 20 Token 买到一句「AI 服务暂不可用」）

- **证据**

  - `backend/.../controller/AssistantController.java:103-106`

        reply = fallbackReply(systemPrompt, message);      // ← 模板兜底文案
        send(emitter, "delta", Map.of("content", reply));

    整段在 `try` 内正常走完 → 切面/显式退款都不触发 → 20 Token 照扣。
  - `RecommendationService.java:338` 同样：`deepSeekService.chat(...)` 返回 null 即降级为规则推荐，`RECOMMEND` 的 15 Token 照扣。

### P0-4 【缺陷】匿名 5 次错密码即可锁死任意账号 30 分钟（含 admin），且无解锁通道

- **证据**
  - `backend/.../service/AuthService.java:35-38` `isAccountLocked` 命中即抛「账户已锁定，请稍后再试」；`LoginAttemptService.java:46-50` `countFailedAttemptsSince(username, now-30min) >= maxAttempts(5)`。
  - `LoginAttemptService.java:73-75` **`resetAttempts` 是空实现**：
    ```java
    public void resetAttempts(String username) { log.info("重置用户 {} 的登录尝试记录", username); }
    ```
    它只在日志里说"重置"，一条记录都没删/没标记。因此成功登录也不会清零，锁定时长从**最后一次失败**起算 30 分钟。
  - 用户不存在也会计数：`AuthService.java:44-48`（`用户不存在` 也走 `recordAttempt`）→ 可锁定尚未注册的、以及 admin 等已知用户名。
  - **实机复现**：student01 连错 5 次 → 第 6 次用**正确密码** `student123` → `HTTP 429 {"message":"账户已锁定，请稍后再试"}`；`login_attempts` 中该用户失败记录 = 5。
- **影响**：安全/可用性。竞品或任意学生写 5 行脚本就能把 `admin`、把竞争对手、把全班同学的账号锁死 30 分钟，平台无解锁接口、后台也无「解锁用户」按钮，运营只能改库。上线即是一个可被公开使用的拒绝服务面。
- **修复**（S/M）：① 用「指数退避 + 验证码」替代硬锁（第 3 次起要求图形/滑块验证，第 8 次起退避）；② 账号永远不硬锁，锁只作用于「该 IP+该账号」组合；③ 真正实现 `resetAttempts`（`loginAttemptRepository.deleteByUsernameAndSuccessFalse(username)` 或 Redis 计数器 `DEL`）；④ 后台加「解锁账号」并记审计。

### P0-5 【缺陷】锁定可被并发绕过；随后 IP 封禁误伤同 IP 全体用户（校园 NAT 场景必炸）

- **证据**
  - `LoginAttemptService.java:30-44`：`@Async public void recordAttempt(...)` —— 失败尝试是**异步**落库的，而 `isAccountLocked/isIpBlocked` 是**同步先读**。读在写之前 → 并发下读到的计数永远是旧的。
  - **实机复现（A）**：对 `student02` 同时发 20 个错误密码 → **20 个全部返回 400「用户名或密码错误，剩余尝试次数: …」**（即全部进入密码比对、无一条被锁），事后 `login_attempts` 里 student02 有 20 条失败记录。
  - `LoginAttemptService.java:52-56` `isIpBlocked = countFailedAttemptsByIpSince(ip, now-15min) >= maxAttempts*3 (=15)`；`AuthService.java:40-42` 命中即抛「IP地址已被临时封禁」。
  - **实机复现（B）**：上述 20 次失败之后，同一台机器用**正确账号密码**登录 → `HTTP 400 {"success":false,"message":"IP地址已被临时封禁"}`。
- **影响**：安全 + 可用性 + 增长。① 暴力破解防护在并发面前等于不存在（每轮 20 次并行猜测）；② 15 次失败就把一个出口 IP 封 15 分钟——高校宿舍/机房/图书馆几乎全在同一个 NAT 出口 IP 后面，**一个脚本能让整所学校 15 分钟登不进来**，且封禁无提示、无白名单、无后台解封。这是本项目目标用户结构下最现实的线上事故。
- **修复**（M）：① 失败计数改为同步/原子（同事务插入，或直接用 Redis `INCR`+`EXPIRE`，读改写原子化）；② IP 维度阈值大幅提高（如 100 次/15 分钟）且只用于「验证码升级」而非直接拒绝；③ 给 IP 封禁加白名单/内网段豁免，并暴露到后台可查看可解除；④ 对 `login` 加边缘限流（nginx `limit_req`，见 P1-2）。

## P1 — 高价值缺失 / 高危但不直接变现

### P1-1 【缺陷】刷新令牌机制实现了但客户端从没用过；登出也不撤销 → 令牌生命周期失控

- **证据**
  - 服务端完整实现了轮换：`AuthService.java:86-106`、`RefreshTokenService.java:27-39`（每次刷新 `revokeAllUserTokens` 后再发新的）。
  - 客户端**一次都没调用**：`frontend/src/lib/api.ts` 全文无 `/api/auth/refresh`；`admin-console/src/lib/auth.tsx:17-20` 只取 `token`，丢弃 `refreshToken`（`LoginResponse` 接口没这个字段）。全仓 grep `refresh` 在 `frontend/src` 只命中无关的 `refreshUnread/refreshBalance`。
  - 登出只清本地：`frontend/src/lib/auth.tsx:52-55` `const logout = () => { clearAuth(); setUser(null); }`；`frontend/src/components/Layout.tsx:115` 调它。**没有** `POST /api/auth/logout`，服务端 refresh token（7 天）与 access token（24 小时）都继续有效。
  - `AuthService.java:108-121` 的 `logout` 逻辑（撤销全部 refresh token）因此是死代码。
- **影响**：安全 + 用户体验。① 用户以为「退出登录」了，实际 7 天内令牌仍可用（机房/图书馆共用电脑场景直接可被冒用）；② 24 小时到期后用户被硬踢回登录页（`api.ts:90-91` 文案「登录已过期，请重新登录」），7 天免登录的体验收益完全没拿到；③ 每 24 小时一次全量重新登录 = 转化漏斗上的额外流失。
- **修复**（S/M）：① 前端接入 `/auth/refresh`：在 `request()` 收到 401 时用 `refreshToken` 静默续期并重放一次请求（需单飞/去重）；② `logout` 先 `await request('/api/auth/logout', {method:'POST', params:{refreshToken}})` 再清本地；③ 顺带修 P1-8 的 401/403 口径。

### P1-2 【缺失】全站没有任何限流：登录、卡密兑换、AI 调用、注册赠送都可被无限刷

- **证据**：全仓 grep `ratelimit|rate-limit|bucket4j|resilience4j|limit_req|Sentinel` 在 `backend/` 与 compose 中**零命中**；`SecurityConfig.java` 无任何限流过滤器；`nginx.conf` 无 `limit_req_zone`。具体暴露面：
  - `/api/auth/register`（`SecurityConfig.java:53` `/auth/**` permitAll）：无图形验证码、无手机/邮箱验证、无 IP 限制，注册即送 50 Token + 每日 5 Token（`BillingDataInitializer.java:78-79`）→ **脚本批量注册即可无限获得免费 AI 额度**（每账号 50 Token ≈ ¥0.5 的 DeepSeek 成本，且有免费额度开关兜底失效的风险）。

- **修复**（M）：① 边缘：nginx `limit_req` 对 `/api/auth/login`、`/api/token/redeem`、`/api/auth/register` 限速（如 10r/m per IP）；② 应用层：引入 Bucket4j/Redis 做「用户维度 + 场景维度」的 AI 调用限流（如每用户每分钟 N 次）；③ 注册加验证码 + 单 IP 每日注册上限；④ 卡密失败 N 次锁定 10 分钟并落审计。

### P1-8 【缺陷】未认证返回 403 而非 401，前端把「登录过期」显示成「没有权限」

- **证据**：**实机复现** `curl /api/token/balance`（无 token / 伪造 token）→ **`http=403`**（不是 401）。原因：`SecurityConfig` 未配置 `AuthenticationEntryPoint`/`AccessDeniedHandler`，Spring Security 默认对匿名请求经 `ExceptionTranslationFilter` 走 403。
  - `frontend/src/lib/api.ts:86-95`：`resp.status === 401 ? '登录已过期，请重新登录' : resp.status === 403 ? '没有权限执行此操作'` → 24 小时令牌到期后，用户看到的是「没有权限执行此操作」，且 `clearAuth()` 不会被调用、不会跳登录页，用户卡在报错页面反复点。
- **影响**：用户体验 + 转化。到期即困惑，且无任何引导重新登录。
- **修复**（S）：后端加 `authenticationEntryPoint` 返回 401（JSON `ApiResponse.error("登录已过期")`），仅授权失败返回 403；前端两个 SPA 统一在 401 时 `clearAuth()` + 跳登录（并顺带接 P1-1 的静默刷新）。

### P1-9 【缺陷】无数据库迁移工具，`ddl-auto=update` 直接跑生产；手写"H2 专用"迁移在 MySQL 上静默失败

- **证据**
  - `backend/pom.xml` 无 flyway/liquibase 依赖（grep 零命中）；`application-prod.yml:24` `hibernate: ddl-auto: update` 仍在用；`application.yml:25`、`application-mysql.yml:21` 同样。
  - 手写迁移只存在于 `config/DataInitializer.java:64-93`，且是 H2 语法：
    ```java
    jdbcTemplate.execute("CREATE TABLE notifications ( id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY, ...)");
    ```
    `GENERATED BY DEFAULT AS IDENTITY` 是 H2/PG 语法，**MySQL 不认**（要 `AUTO_INCREMENT`）；而整个方法被 `catch (Exception e) { log.warn("通知表迁移检查失败(可忽略): {}", ...) }`（`:90-92`）包住 → **在 MySQL 上会失败并且只打一行 WARN，运营完全不会注意**，`notifications` 表的枚举 CHECK 约束（不含 `ACCEPTED`）也就永远修不好。
  - `spring.sql.init.mode: never`（`application.yml:32-34`）——连 SQL 初始化都关了，没有第二条迁移路径。
- **影响**：数据一致性 + 运维。① 生产加字段/改类型/加索引全靠 Hibernate 猜，改列类型/删列的行为不可控且**不可回滚**；② 多实例滚动发布时并发 DDL 有锁表风险；③ 上面这条迁移是「以为自己修好了、其实没修」的典型。
- **修复**（M）：引入 Flyway（`spring-boot-starter`+`flyway-core`），`ddl-auto: validate`，把现有 schema 用 `V1__baseline.sql` 打底，`migrateNotificationSchema` 改写成 `V2__notif_enum.sql`（区分 H2/MySQL 方言或用 `vendor` 目录）。至少也要把那段 try/catch 的失败升级为启动失败。

- **证据**

### P1-12 【缺陷】SSE 跑在 `ForkJoinPool.commonPool`，与 `@Async` 线程池互相拖累；无背压、无限流、无超时中断

- **证据**
  - `AssistantController.java:86,150`、`PreparationPlanController.java:65` 全部用 `CompletableFuture.runAsync(...)`（无 executor 参数）→ 公共 ForkJoinPool，并行度 = CPU 核数 - 1。文档里的生产机是 2C2G（`阿里云上线指南.md:119`）→ **全平台同时只能有 1 个 AI 流式请求**，第 2 个用户开始排队，队列是无界的。
  - `@EnableAsync`（`config/AsyncConfig.java:8`）与 `@Async`（`LoginAttemptService.java:30`、`AuditService.java:26`）没有自定义 `TaskExecutor` → 用 Boot 默认的 `applicationTaskExecutor`（core=8、queue 无界），与 SSE 抢同一批线程资源。
  - 客户端断开不影响上游：`send()`（`AssistantController.java:255-261`）把发送失败降级成 `log.debug` 后**继续跑**；`DeepSeekService.chatStream`（`:110-129`）没有取消钩子 → 用户点了「暂停」（`AssistantPage.tsx:282-302` abort）之后，服务端仍会把整段 LLM 输出读完并 `updateAssistantMessage(slot, full)`（`:109`）**覆盖**前端刚回写的部分内容，导致「继续生成」从完整文本后再续写。
- **影响**：规模化 + 成本 + 用户体验。2 核机器上 1 个并发就会让 AI 页面集体转圈（P0 级可用性，与 P0-1~P0-3 叠加会放大投诉）；断流不中断上游 = 白付 DeepSeek 费用；暂停/续写的语义被破坏。
- **修复**（M）：① 定义专用 `sseExecutor`（如 core=8/max=32/有界队列+CallerRuns）并显式传入 `runAsync`；② `@Async` 各自线程池（审计写入、登录尝试分离）；③ `send()` 失败或客户端断开时通过 `AtomicBoolean cancelled` 让 `chatStream` 的 `onDelta` 抛出以中止读取；④ 给每个用户/每个会话加并发上限。
  （注：此项与并行审计的 AI 维度结论一致，此处从运维/并发容量角度补证。）

### P1-13 【缺失】个人信息保护（PIPL）几乎空白：无隐私政策/同意、无账号注销、数据出境无告知

- **证据**
  - 前端全仓 grep `隐私|用户协议|同意` **零命中** → 注册页没有任何隐私政策勾选或告知。
  - 但注册接口接收手机号与学号：`AuthController.java:49-50` `user.setPhone(request.getPhone()); user.setStudentId(request.getStudentId());`（`RegisterPage.tsx` 目前没渲染这两个输入框，但接口接受，且我实机用它们注册成功了 → 等于无同意收集敏感个人信息）。
  - 无自助注销/导出：`/users/**` 只有 ADMIN 能进（`SecurityConfig.java:81`），用户自己**无法删除账号或导出个人数据**；`UserController.java:103-108` 的删除是管理员接口，且**不清理该用户的上传文件、Token 账户、流水**（`token_account.user_id` 无外键、`token_transaction` 保留，删除后余额/流水成孤儿）。
  - 数据出境：用户上传的备赛资料全文（`DocumentService.java:39` 最多 10000 字）与画像/团队/项目上下文一起进入 DeepSeek 请求体（`AssistantService.buildSystemPrompt → buildContextString`），境内无告知、无脱敏开关。
- **影响**：合规 + 信任。手机号+学号是《个人信息保护法》下的敏感个人信息，无告知同意即收集属违规；无注销路径直接违反「删除权」。一旦被投诉或检查，属硬伤。
- **修复**（M）：① 注册页加隐私政策勾选（不勾不能提交），政策中列明「收集手机号/学号/上传资料」及用途；② 提供「AI 请求最小化」：发给 LLM 的上下文剥离真实姓名/手机号/学号（只保留专业、年级等必要维度），并在上传资料处提示"将发送给第三方大模型"；③ 用户端加「注销账号」+ 数据导出（JSON）；④ 删除用户时级联清理上传文件与 Token 账户/流水（或改为软删 + 匿名化）。

## 已实现得不错的部分（同法验证，非客套）

1. **卡密并发核销是真原子的**。`CardKeyRepository.findByCodeForUpdate`（`@Lock(PESSIMISTIC_WRITE)` + `select c from CardKey c where c.code = :code`）+ `TokenService.redeemCard` 的「锁内二次判状态」写法正确。**实测**：同一张卡密 4 个并发请求 → `1 × 200 兑换成功` + `3 × 400 该卡密已被使用`，余额只加一次（`totalRecharged 1200` = 两张卡各一次）。
2. **订单确认收款幂等**。`RechargeOrderRepository.findByIdForUpdate` + `confirmOrder` 的「PAID 直接返回」状态机正确。**实测**：同一订单 4 个并发 confirm → 全部 200，但 `token_transaction` 里 `RECHARGE` 只有 1 条、金额 600，余额只入账一次。
3. **`@CostTokens` 的异常退款链路是通的（在真的抛异常时）**。**实测**：`POST /preparation-plans/999999/tasks/999999/swap` → `400 计划不存在`，流水成对出现 `CONSUME TASK_SWAP -5` + `REFUND TASK_SWAP +5 失败自动退款`。问题只在于「很多人为吞掉异常/走到早退分支」，而不是切面本身。
4. **资金权限边界清晰**。**实测**：学生 token 访问 `/api/users` → 403，访问 `/api/admin-api/billing/overview` → 403；`SecurityConfig.java:81,84` 的 `/users/**` 与 `/admin-api/**` → `hasRole("ADMIN")` 生效顺序也对（学生规则显式排在管理员规则之前，`SecurityConfig.java:67-74`）。
5. **上传落盘安全**：`DocumentService.java:69` 用 `UUID + 白名单扩展名（txt/md/pdf）` 作为落盘名，按 `userId` 分目录并用 `toAbsolutePath().normalize()`（`:71`），没有路径穿越；`/uploads/**` 虽在 `SecurityConfig.java:58` 放开，但 `StaticResourceConfig` **没有**注册 `file:/app/uploads/` 的 handler（只有 `/app/static/`），所以上传文件实际不可被匿名直读（这点容易被误判成漏洞，实测无此问题）。
6. **密码存储正确**：`SecurityConfig.java:34-36` `BCryptPasswordEncoder`；`User.java:32-34` `password` 上有 `@JsonIgnore`，实测 `/users/search`、`/auth/register` 等响应都不含密码字段。
7. **前端金额/数字格式统一**：`admin-console/src/lib/api.ts:132-150` 的 `fmtYuan/fmtNum/fmtTime` 与 `TX_TYPE_META/SCENE_META/ORDER_STATUS_META` 集中在一处，后台各页复用，没有散落的硬编码价格数字（价格全部来自接口）。
8. **`@CostTokens` 设计本身是对的**：把计费横切到注解上，业务代码零侵入；`isBillingEnabled()`（`TokenService.java:75-79`）在未配置 `DEEPSEEK_API_KEY` 时自动免扣，避免了「开发环境被计费逻辑挡住」；402 语义（`GlobalExceptionHandler.java:99-105`）+ 前端引导充值（`AssistantPage.tsx:405`）这条链路设计得比多数同类项目干净。
9. **部署产物管理干净**：`git ls-files` 确认 `dist/`、`target/`、`*.jar`、`deploy/stage/`（含 92MB 的 `app.jar`）**都没有入库**（`.gitignore:2-9`），仓库只有 284 个跟踪文件；`deploy/stage/Dockerfile:14,23` 用非 root 用户 `spring` 运行，容器里没有编译工具链。
